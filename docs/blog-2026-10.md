# Blog section: architecture, standards and first ten posts (October 2026)

Status: **built, verified, awaiting merge.** Ten posts across five clusters, plus an
index and five cluster hubs. Generated by the existing zero-dependency builder in
`tools/build_site.py`; nothing in `website/` is hand-edited.

---

## 0. Why a blog, and why not on the homepage

The knowledge base under `/resources/` answers *how a mechanism works*. It is
reference material: long, technical, one article per topic. What it does not do is
give a small-business reader a sequence to follow, a command to run, or a decision
at the end.

The blog is that layer, and it is deliberately a separate section rather than a
block on the homepage:

- **Search intent is per-question.** "How do I set up DMARC without breaking my
  email" and "what is DMARC alignment" are different queries. One page cannot
  answer both well, and funnelling every topic to `/` would make the homepage
  compete with itself.
- **Clusters beat a feed.** Every post belongs to one of five clusters. Each cluster
  has a hub that collects its guides, the controls an external assessment measures
  in that area, and the reference article behind it. Hubs link out to each other,
  and posts link up to their hub and across to their reference article.
- **The homepage is unchanged.** No section was added to `/`; the section is
  reachable from the primary navigation and the footer `Resources` column, which is
  the same access path as the knowledge base.

## 1. URLs and redirects

| Path | Page |
|---|---|
| `/blogs/` | Index: start-here posts, five cluster cards, all ten posts, editorial standard |
| `/blogs/<cluster>/` | Hub: intro, its posts, the controls that cluster maps to, other clusters |
| `/blogs/<slug>/` | Post: byline, standfirst, "the short version", body with TOC, control block, related posts, CTA |
| `/blog/` | Static redirect to `/blogs/` (was a redirect to `/resources/`) |

`/blog/` previously pointed at the knowledge base because no blog existed. Now that
one does, the legacy path redirects to the section it always meant. The three old
`/blog/<article>/` redirects are untouched: those specific articles still live in
`/resources/` and nothing about them changed.

No existing URL was moved or removed, and no redirect target now points at a page
that does not exist (the link checker verifies every internal `href`).

## 2. How it is built

| File | Role |
|---|---|
| `tools/sitegen/blog/__init__.py` | Cluster definitions, post aggregation, reading-time maths, a small import-time integrity check |
| `tools/sitegen/blog/email_security.py` | Three posts (body HTML + metadata) |
| `tools/sitegen/blog/dns_security.py` | One post |
| `tools/sitegen/blog/website_security.py` | One post |
| `tools/sitegen/blog/smb_basics.py` | One post |
| `tools/sitegen/blog/assessment.py` | Four posts |
| `tools/sitegen/pages_blog.py` | Index, hubs, article template, TOC extraction, post cards |
| `tools/sitegen/schema.py` | `blog_posting()` and `blog_collection()` |
| `tools/build_site.py` | Registers the 16 new pages, adds posts to the sitemap, rewrites the `/blog/` redirect |

A post is a dictionary:

```python
{
    "slug": "set-up-dmarc-without-breaking-email",
    "cluster": "email-security",
    "title": "…",            # <h1> and BlogPosting headline
    "seo_title": "…",        # <title>, og:title, page node name (≤65 chars)
    "desc": "…",             # meta description, og:description (60–165 chars)
    "lede": "…",             # standfirst, plain text
    "date": "2026-10-31",
    "updated": "2026-10-31",
    "takeaways": ["…", …],   # rendered as "The short version"
    "body": "<p>…</p>",      # h2 / h3 / p / ul / ol / table / pre only
    "related": ["slug", …],  # posts, resolved to cards
}
```

Heading ids and the table of contents are generated from the `<h2>` elements at
render time, so a post never hand-maintains anchors. Numeric heading text
("1. The metadata block") is stripped to a letter-first id, which is what
`html-validate`'s `valid-id` rule requires.

The template appends a standard **"What SMB Scanner Lite checks here"** section to
every post, built from the cluster's `checks` list. That block is visible prose, a
table, and a link to `/capabilities/` — it is not a banner.

Reading time is `round(words / 210)`, minimum three minutes, computed from the
stored body rather than estimated by hand. `wordCount` and `timeRequired` in the
structured data come from the same number, so the page and the markup cannot drift.

## 3. Editorial standard

Applied to all ten posts:

- **No invented evidence.** No breach statistics, no "studies show", no customer
  stories, no benchmark numbers, no fabricated citations. Where a figure appears it
  is either arithmetic from the published catalog (22 controls, five categories,
  grade bands) or a value quoted from the published recorded assessment (86/100,
  grade B, eight concluded controls, two warnings).
- **Commands instead of hand-waving.** Where a check can be run by hand, the query
  is in the post: `dig +short TXT`, `curl -sSIL`, `openssl s_client`. Where it
  cannot, the post says so.
- **The limit is stated in the same breath as the capability.** Every post that
  mentions a check also names what it cannot see.
- **Authorisation is explicit.** Posts assume the reader owns the domain. Each one
  links to `/responsible-use/`, and the control block repeats it.
- **No ranking or rich-result promise.** Nothing claims a position, a rich result,
  or a timeline.
- **Freshness.** Publication and last-updated dates are printed, followed by the next
  scheduled review. The three email guides name provider-specific selectors and console
  paths, so they are on a six-month cycle (next review 30 April 2027); everything else is
  annual. The date is a commitment in the page footer, not a claim that a review happened.
- **Byline.** A real person (`AUTHOR` in `tools/sitegen/config.py`), linked to the
  repository. No invented job titles, credentials or industry experience.

Every post ends with the same CTA: request a private assessment of your own domain,
or open the recorded one.

## 4. Structured data

Published per page:

| Page | Nodes added to the site-wide graph |
|---|---|
| `/blogs/` | `CollectionPage` + `Blog` (10 inline `BlogPosting` entries) + `BreadcrumbList` |
| `/blogs/<cluster>/` | `CollectionPage` + `Blog` (that cluster's posts) + `BreadcrumbList` |
| `/blogs/<slug>/` | `WebPage` + `BlogPosting` + `BreadcrumbList` |

`BlogPosting` carries `headline`, `description`, `datePublished`, `dateModified`,
`author` (Person), `publisher` (`#organization`), `mainEntityOfPage`, `inLanguage`,
`articleSection`, `wordCount`, `timeRequired`, `isAccessibleForFree` and an
`isPartOf` reference to its cluster blog node.

Two deliberate choices:

1. **`blogPost` entries are inline nodes, not `{"@id": …}` references.** Each post
   lives on its own page, and this site publishes a single-page `@graph`; a bare
   cross-page reference would dangle and the audit fails on exactly that.
2. **No `image` on `BlogPosting`.** Google's Article guidance treats `image` as
   required for the Article rich result. The site has one social card, not a
   per-post image, and attaching an unrelated picture would make the markup claim
   something the page does not show. The consequence is recorded here rather than
   hidden: **blog posts are not eligible for the Article rich result** until a real
   per-post image exists. Social sharing still uses the site card through
   `og:image`, which is truthful for every page.

The audit (`--audit`) checks all of this on every build: one JSON-LD block, no
dangling `@id`, no `Product`/`Offer`/`AggregateRating`/`Review`, absolute URLs,
sequential breadcrumb positions, a visible breadcrumb to match the markup, and a
page node of an allowed type.

## 6. Deliberately not included

| Not built | Why |
|---|---|
| RSS/Atom feed | Nothing generates or consumes one yet, and a stale feed is worse than none. A static `feed.xml` is straightforward to add later; it would need the same date discipline. |
| Comments | Requires a third-party service, which would break the "no third-party origins" property established in the September remediation. |
| Tag pages, author pages, pagination | Five clusters and ten posts do not need them. Tags would create thin, overlapping pages that compete with the hubs. |
| Newsletter capture | No list exists, and adding a form would imply a commitment to send. |
| Per-post social images | See §4. This is the one gap that materially limits distribution. |
| A "backlog" or "coming soon" list | Placeholder promises age badly and add nothing a reader can use. The remaining titles stay in the outreach plan until each one is written. |

## 7. Adding the next post

1. Pick the cluster. If none fits, the post probably belongs in `/resources/` as a
   reference article instead — check first.
2. Add a dictionary to the matching `tools/sitegen/blog/<cluster>.py`:
   `slug`, `cluster`, `title`, `seo_title` (≤65), `desc` (60–165), `lede`, `date`,
   `updated`, `takeaways`, `body`, `related`.
3. Body rules: `<h2>` for sections (ids are generated), `<h3>` for subsections, no
   `<h1>`, no inline styles, no external `http://` links, no placeholder links.
   Escape `&` as `&amp;`.
4. Run the build, then the three checks:

   ```bash
   python3 tools/build_site.py --check --audit
   npx html-validate "website/**/*.html"      # with the project's rule config
   node smoke.mjs                             # jsdom DOM + structured-data checks
   ```

5. Update the post's `updated` only when the content actually changes, and add it
   to the sitemap automatically (it is derived from the registry).

The import-time assertions in `tools/sitegen/blog/__init__.py` fail the build if a
post names an unknown cluster, reuses a slug, or links to a post that does not
exist.

## 8. Outstanding

1. **Per-post images.** The only item that blocks Article rich-result eligibility
   (§4). A 1200×630 card per post, generated once and committed, would fix it; the
   current image tooling is not part of the repository, so this is a separate task.
2. **No live measurement of the section.** The sandbox cannot reach
   `smbscannerlite.me` and has no browser, so there is no Lighthouse run, no field
   data and no impression data for these pages. Publishing is not evidence of
   ranking.
3. **Search Console.** Nothing has been submitted, inspected or validated for these
   URLs. Do not describe the section as indexed until Search Console says so.
4. **Content ages.** Provider interfaces (Google Workspace, Microsoft 365 selector
   names) and browser defaults change. The posts name the specific values, which
   helps a reader spot drift, but the review dates are the only guarantee — keep
   them honest.
