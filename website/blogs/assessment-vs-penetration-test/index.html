External security assessment vs penetration testing

Both produce a document with findings in it, which is why they get confused in procurement conversations. The difference is what a tester is allowed to do, and what question the engagement is answering.

By Muhammad Atif Published 31 October 2026 4 min read

The short version

  • An external assessment checks whether the outside is configured correctly. A penetration test tries to break in.
  • A penetration test needs written authorisation and a scope document before anything happens. Unauthorised testing is not testing.
  • An assessment is repeatable and cheap enough to run quarterly; a pentest is an event, usually annual or change-triggered.
  • Neither replaces the other, and one report should never be presented as the other.

The distinction is easiest to hold onto as a question. An external assessment asks: is this configured the way it should be, and can anyone see otherwise? A penetration test asks: given a motivated person and permission to attack, can they get in? The first is breadth. The second is depth.

Why the confusion exists

Three reasons. Both produce "findings". Both are sold by the same kinds of provider. And many vendors describe automated configuration checks as "penetration testing" because the phrase carries more weight with a buyer who has one line item for security.

That inflation is not harmless. A business that believes a header scan was a penetration test skips the engagement that would have found the authorisation bug in its customer portal. A business that believes a pentest covers its email spoofing exposure gets a clean report and no DMARC record.

What a penetration test finds that an assessment never will

  • Broken access control: one customer reading another's invoice by changing an ID.
  • Authentication weaknesses: password reset flows, session fixation, token handling.
  • Business logic abuse: refunds, discounts, workflow bypasses.
  • Chained exploits where each step is unremarkable and the combination is not.
  • Insider and social engineering paths, if that is in scope.

None of that is visible to an anonymous request, which is exactly why an assessment cannot claim to cover it.

What an assessment does that a pentest will not

  • Cover every domain you own, not just the one in scope, for roughly the effort of one.
  • Detect drift: the DMARC record that was tightened and then quietly loosened six weeks later.
  • Produce a comparable number each quarter, so a trend exists at all.
  • Give a non-specialist a starting point that does not require reading an exploit write-up.

Drift is the underrated half. Most small business exposure is not a clever attack; it is a control that was correct in March and is not in September, because someone changed a DNS host or renewed a certificate through a different provider.

When you need which

What the two artefacts actually look like

The formats differ as much as the methods. Illustrative shapes below, not real engagements:

Evidence: header absent on the static response.
Action: publish a policy in report-only mode, then enforce.		 “Access control bypass in invoice view”
Method: changed an object identifier in the request.

The first can be fixed in a deployment and re-checked with one command. The second cannot be found by any amount of header inspection, and cannot be fixed without changing application code. Both are useful; neither substitutes for the other.

Authorisation is not a formality

A penetration test without written authorisation is not a penetration test, it is an attack with a report attached. Scope, testing windows, excluded systems, data handling and an emergency contact belong in a document both sides sign before the first packet. It is also why "we ran a pentest on a supplier's portal to see" is a bad idea regardless of intent — see responsible use.

An external assessment sits at the low end of that spectrum: it reads what you publish and makes ordinary requests. Authorisation is still the right starting point, and this project records consent before a scan of any kind. That is a design decision, not paperwork.

How they fit together

The pattern that works for a small business is a cadence, not a purchase: an external assessment each quarter as a baseline and a drift check, and a penetration test when the application changes materially, before a launch, or annually if a customer or insurer requires it. Findings from either should end up in the same register, with an owner and a date, or neither will be fixed.
