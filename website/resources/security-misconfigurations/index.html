Misconfiguration evidence: what it proves

Interpret common public security misconfigurations without equating missing headers, unusual ports or stale DNS records with confirmed compromise.

Online scan status

Observation is the first step

A configuration assessment can reveal a published record that contradicts a policy, a TLS certificate that does not cover the requested hostname, or an HTTP response that lacks a relevant security header. Each case needs the exact response and a defined rule; labels like 'unsafe' without evidence are too broad to guide remediation.

Severity depends on context

A missing HSTS header on a production login page warrants different attention from a test endpoint with no authentication. A public management port deserves review, but reachability alone is not proof of an exploitable service.

Do not infer an incident

Misconfiguration is a state, not evidence that an adversary exploited it. Confirm the owner, exposure, business consequence and any compensating controls before describing the impact.
